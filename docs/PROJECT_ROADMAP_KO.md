# Paper Citadel 장기 개발 계획서

- 문서 버전: 0.1
- 작성일: 2026-07-10
- 대상: 투자 검토용 베타, 사업 제안용 실증 버전, 장기 개발 기준 문서
- 현재 단계: 플레이 가능한 기술·게임성 프로토타입

## 1. 문서 목적

이 문서는 Paper Citadel을 단기간에 기능만 늘리는 프로토타입이 아니라, 장기간 검증하고 개선할 수 있는 웹 기반 PvPvE 던전 RPG로 발전시키기 위한 기준을 정한다.

계획의 핵심은 다음과 같다.

1. 현재 플레이 가능한 버전을 보존한다.
2. 한 번에 하나의 핵심 시스템만 완성한다.
3. 각 단계마다 플레이 테스트와 완료 기준을 둔다.
4. 기술 안정성, 게임성, 시각 품질을 함께 관리한다.
5. 투자나 지원사업 제안 전에 실제 사용자 데이터와 검증 결과를 확보한다.

이 일정은 1인 중심의 파트타임 개발을 기준으로 약 14~24개월을 가정한다. 전담 인력이나 외부 아트·서버 지원이 확보되면 단축할 수 있지만, 일정 단축보다 단계별 완성도를 우선한다.

## 2. 제품 비전

### 핵심 문장

> 설치 없이 링크로 접속해 인간과 오크 진영을 선택하고, 거대한 공유 던전에서 무기와 골드를 파밍하며 발록과 상대 진영 성채를 공략하는 상시 PvPvE 웹 RPG.

### 핵심 경험

- 이름을 입력하고 즉시 접속한다.
- 넓은 던전을 탐험하며 몬스터와 중간보스를 사냥한다.
- 서로 다른 공격 방식의 무기를 획득하고 교체한다.
- 골드를 개인 장비 또는 진영 방어에 투자한다.
- 발록을 처치해 공용 던전 단계를 높인다.
- 인간과 오크가 상대 성문을 파괴하고 진영 대장을 공략한다.
- 죽더라도 자기 진영의 부활 성소에서 다시 출발한다.
- 던전은 라운드 종료 없이 계속 유지된다.

### 제품 차별점

- 설치와 가입이 필요 없는 브라우저 진입성
- 레트로 1인칭 던전 탐험과 실시간 멀티플레이 결합
- PvE 사냥, 중립 보스 레이드, 진영 공성전이 한 공간에서 공존
- 개인 성장과 진영 성장을 함께 선택하는 골드 경제
- 종이성채만의 귀엽고 강한 캐릭터 실루엣

## 3. 개발 원칙

### 3.1 항상 플레이 가능한 메인 버전 유지

- 실험적인 렌더링과 대규모 기능은 별도 작업본에서 검증한다.
- 실제 화면 확인 없이 메인 버전에 시각 변경을 배포하지 않는다.
- 중요 단계마다 Git 태그와 릴리스를 생성한다.
- 배포 전 클라이언트 문법, 서버 실행, 저장, 접속, 사망·부활을 확인한다.

### 3.2 기능보다 핵심 경험 우선

- 신규 몬스터 수보다 전투 선택과 보상 차이를 우선한다.
- 큰 맵은 빈 공간이 아니라 구역, 목표, 지름길을 포함해야 한다.
- 무기는 공격력 숫자만 다른 복제품이 아니라 플레이 방식이 달라야 한다.
- UI는 기능을 설명하는 장식이 아니라 판단과 행동을 돕는 도구여야 한다.

### 3.3 단계 종료 조건 준수

- 완료 기준을 통과하지 못하면 다음 대형 단계로 넘어가지 않는다.
- 심각한 저장 손실, 접속 불가, 전투 판정 오류는 신규 기능보다 먼저 수정한다.
- 플레이 테스트에서 반복적으로 혼란을 주는 기능은 과감히 축소하거나 제거한다.

### 3.4 투자·사업 제안에 필요한 기록 유지

- 사용한 외부 코드, 폰트, 이미지, 라이브러리의 출처와 라이선스를 기록한다.
- 기능별 개발 목적과 검증 결과를 문서화한다.
- 테스트 인원, 세션 길이, 이탈 지점, 오류 수를 가능한 범위에서 측정한다.
- 기술적 성과와 게임 콘텐츠 성과를 구분해 설명한다.

## 4. 현재 프로토타입 평가

### 확보된 기반

- Canvas 2D 기반 레이캐스팅 1인칭 렌더링
- 플레이어 이동, 충돌, 일반·특수공격, 광폭화
- 몬스터 AI, 원거리 공격, 중간보스와 발록
- 경험치, 레벨, 체력, 방어구, 아이템 드랍
- Socket.IO 기반 멀티플레이 동기화
- 서버 권위 몬스터 HP, 사망, 리스폰, 던전 단계
- 캐릭터명 기반 저장과 브라우저 복구 보조 장치
- GitHub Pages 클라이언트와 Render 서버 배포 구조
- 캐릭터와 몬스터 PNG 스프라이트 기반 표현

### 핵심 위험

- Render의 비영구 파일 시스템에 의존하는 저장 구조
- 브라우저 백업이 서버 저장을 보조하는 임시 구조
- 약 20만 자 이상의 단일 `game.js`에 기능이 집중됨
- 일부 한글 문자열과 README 인코딩 손상
- 렌더링, UI, 스프라이트 품질의 편차
- 자동화된 회귀 테스트 부족
- PvP와 아이템 경제를 추가하기 전 서버 판정 구조 보강 필요
- 기존 무기 강화 데이터를 새 무기 시스템으로 이전해야 함

## 5. 목표 베타 범위

투자·사업 검토용 베타는 아래 경험을 5~20명이 안정적으로 플레이할 수 있어야 한다.

1. 인간 또는 오크 진영 선택
2. 진영별 부활 성소와 안전구역
3. 여러 사냥 구역을 포함한 대형 공유 던전
4. 장검, 대검, 창, 도끼, 망치 획득과 교체
5. 개인 인벤토리, 골드, 대장장이 강화와 판매
6. 중간보스와 발록 레이드
7. 상대 진영 플레이어와의 서버 권위 PvP
8. 파괴 가능한 성문과 진영 수비대
9. 기사단장과 오크대장 공략
10. 진영 금고, 대장 강화, 용병 고용
11. 영구 저장, 재접속, 서버 재시작 복구
12. 일관된 그래픽, UI, 온보딩과 한국어 문구

## 6. 단계별 로드맵

### 0단계. 기준선 보존과 기술 안정화

예상 기간: 4~6주

#### 목표

현재 프로토타입을 잃지 않고 앞으로 확장할 수 있는 안정적인 기준선을 만든다.

#### 주요 작업

- 현재 플레이 버전을 태그로 보존
- README와 게임 내 깨진 한글 문자열 복구
- `game.js`의 렌더링, 입력, 네트워크, UI, 게임 규칙 영역 분리 계획 수립
- 중복 HUD 및 사용하지 않는 렌더링 함수 정리
- 서버 데이터 저장을 PostgreSQL, SQLite 영구 볼륨 또는 외부 관리형 DB로 이전
- 캐릭터와 공용 던전 상태의 저장 책임을 서버로 일원화
- 서버 버전, 저장 상태, 복구 상태를 확인할 수 있는 진단 정보 추가
- 최소 회귀 테스트 작성
- 자산 목록과 라이선스 문서 작성

#### 필수 테스트

- 같은 이름으로 재접속 시 캐릭터 상태 유지
- 서버 재시작 후 캐릭터와 성채 단계 유지
- 두 명 이상 접속, 이동, 공격, 몬스터 사망 동기화
- 발록 처치, 리스폰, 단계 상승과 저장
- 사망 후 체력 회복 및 부활

#### 완료 기준

- 서버를 의도적으로 3회 재시작해도 핵심 데이터 손실 없음
- 치명적 콘솔 오류 없음
- 한글 깨짐 없음
- 안정화 버전 태그 생성

### 1단계. 게임 설계 확정과 데이터 구조 재설계

예상 기간: 3~4주

#### 목표

대형 맵과 무기 경제를 구현하기 전에 변경 비용이 큰 규칙을 문서와 데이터 구조로 확정한다.

#### 주요 작업

- 핵심 게임 디자인 문서 작성
- 인간·오크 진영 규칙 확정
- 맵 전체 구조와 구역 연결도 확정
- 무기 종류별 공격력, 속도, 사거리, 판정, 특수공격 정의
- 아이템 등급과 특성 범위 정의
- 골드 획득량과 소비처 초안 작성
- 인벤토리 용량과 장착 규칙 확정
- 기존 강화 데이터의 이전 정책 확정
- 캐릭터, 무기, 인벤토리, 진영, 던전 상태의 서버 데이터 모델 작성

#### 핵심 결정안

- 무기 종류: 장검, 대검, 창, 도끼, 망치
- 무기 등급: 일반, 고급, 희귀, 영웅, 전설
- 무기 강화: 우선 최대 +15, 실패 없음
- 장착 무기 1개, 빠른 슬롯 3~5개, 가방 10칸부터 시작
- 멀티플레이 무기 드랍은 개인 전리품
- 기존 검 강화 수치는 유산 무기와 골드로 변환

#### 완료 기준

- 주요 수치와 규칙에 미정 항목이 없음
- 서버 저장 스키마와 마이그레이션 문서 완성
- UI 와이어프레임과 맵 연결도 완성

### 2단계. 무기·인벤토리·골드 수직 구현

예상 기간: 6~10주

#### 목표

기존 단일 무기 강화 구조를 파밍과 교체 중심 구조로 전환한다.

#### 2-1. 무기 전투 프로토타입

- 장검, 대검, 창 3종 우선 구현
- 무기별 일반공격과 특수공격 차별화
- 서버 권위 사거리, 각도, 피해량 판정
- 1인칭 무기 스프라이트와 타 유저 장착 무기 표시
- 공격 모션과 피격 반응 정리

#### 2-2. 아이템과 인벤토리

- 고유 ID를 가진 무기 데이터 생성
- 개인 전리품 드랍
- 우측 빠른 무기 슬롯 UI
- `I`키 전체 인벤토리
- 장비 비교, 장착, 잠금, 버리기
- 인벤토리 가득 참 처리

#### 2-3. 골드와 대장장이

- 몬스터 레벨과 등급에 따른 골드 보상
- 골드 자동 획득
- 대장장이 NPC와 강화 UI
- 무기 가치·등급·강화 단계 기반 비용 계산
- 불필요한 무기 판매
- 기존 주문서 드랍 제거 및 보유 주문서 골드 변환

#### 완료 기준

- 플레이어가 사냥으로 세 종류 이상의 무기를 획득하고 교체 가능
- 재접속 후 인벤토리, 장착 무기, 골드, 강화 상태 유지
- 각 무기의 전투 방식이 플레이 테스트에서 구분됨
- 골드의 획득과 소비가 정상 순환함

### 3단계. 대형 던전과 탐험 구조

예상 기간: 8~12주

#### 목표

맵을 단순 확대하지 않고 이동, 발견, 전투, 귀환이 연결되는 모험 공간으로 재구성한다.

#### 권장 구조

- 서쪽 인간 성채 예정지
- 동쪽 오크 성채 예정지
- 북부 해골 묘역
- 중앙 폐허와 워록 제단
- 남부 오우거 동굴
- 심연의 문과 발록 지역
- 중간보스방, 보상방, 숨겨진 길
- 사망 후 재도전을 위한 지름길과 중간 관문

#### 주요 작업

- 현재 대비 3~4배 규모의 월드 설계
- 좌표 하드코딩 대신 구역 ID 기반 시스템 도입
- 구역별 몬스터와 드랍 테이블
- 랜드마크, 조명색, 벽 장식, 바닥색 차별화
- 목표 방향과 거리 안내
- 미니맵 가독성 개선
- 중간보스 처치 시 지름길 개방
- 대형 맵에서 몬스터 AI와 렌더링 성능 최적화

#### 완료 기준

- 신규 플레이어가 안내 없이 주요 구역과 발록방을 찾을 수 있음
- 구역별 시각과 몬스터 구성이 구분됨
- 빈 복도를 오래 걷는 구간이 없음
- 죽은 뒤 핵심 전투로 복귀하는 시간이 과도하지 않음
- 저사양 일반 노트북에서 목표 프레임 유지

### 4단계. 진영과 서버 권위 PvP

예상 기간: 8~12주

#### 목표

인간과 오크가 같은 던전을 공유하며 경쟁할 수 있는 안전한 PvP 기반을 구축한다.

#### 주요 작업

- 캐릭터 생성 시 인간·오크 선택
- 진영별 외형, 이름표, 미니맵 표시
- 양쪽 부활 성소와 안전구역
- 성소는 해당 진영만 출입 가능
- 성소 내부 공격 및 외부 공격 차단
- 플레이어 공격 판정을 서버 권위로 전환
- 아군 공격 방지
- PvP 전용 능력치 압축과 레벨 차이 보정
- 사망, 부활, 무적 보호, 자기 진영 복귀
- 반복 처치 보상 감소와 입구 학살 방지
- 명예 점수 기초 구조

#### 완료 기준

- 위치 조작만으로 다른 플레이어를 공격할 수 없음
- 벽 너머 및 안전지대 공격이 차단됨
- 고레벨이 저레벨을 한두 번에 처치하지 않음
- 10명 전투에서 치명적인 동기화 오류 없음

### 5단계. 성문·진영 대장·공성전

예상 기간: 8~12주

#### 목표

상대 진영 성채를 침공하는 장기 목표를 완성한다.

#### 거점 구조

1. 진영 전용 부활 성소
2. 상점과 대장장이가 있는 안전구역
3. 대장 집무실
4. 용병 안뜰과 수비 구역
5. 파괴 가능한 외곽 성문
6. 공용 던전으로 이어지는 출구

#### 주요 작업

- 아군 통과, 적군 충돌이 적용되는 성문
- 성문 HP, 피해 감소, 파괴, 재건
- 망치와 도끼의 공성 보너스
- 성문 공격 진영 알림과 미니맵 경고
- 기사단장과 오크대장 AI 및 고유 기술
- 대장 사망, 처치 기록, 리스폰 타이머
- 처치될수록 강해지는 대장 성장
- 발록 처치 횟수와 진영 대장 처치 횟수 분리 저장
- 공격 기여도 기반 개인 보상

#### 대장 고유 전투 방향

- 기사단장: 방패 돌진, 방어 태세, 기사 소환, 회복 깃발
- 오크대장: 도끼 강타, 광폭화, 전투 함성, 광전사 소환

#### 완료 기준

- 공격팀이 성문부터 대장방까지 끊김 없이 침공 가능
- 부활 성소 학살과 성문 끼임 현상 없음
- 대장 처치와 리스폰이 모든 접속자에게 동기화됨
- 서버 재시작 후 성문, 대장, 처치 횟수 복구

### 6단계. 진영 경제와 용병 시스템

예상 기간: 6~10주

#### 목표

골드를 개인 성장뿐 아니라 진영 방어에 투자할 수 있게 한다.

#### 주요 작업

- 진영별 공용 금고
- 병참장교 NPC
- 특정 강화 항목에 기부하는 목표형 UI
- 대장 HP, 방어력, 공격력, 지휘력 강화
- 성문 HP, 피해 감소, 자동 수리 강화
- 방패병, 궁수, 사제, 마법사, 정예병 용병
- 용병 배치 한도와 계약 시간
- 접속 인원 차이에 따른 열세 진영 비용 보정
- 진영 금고 지출 기록과 악의적 소비 방지

#### 권장 규칙

- 개인이 공용 금고를 직접 자유 지출하지 않음
- 목표 금액이 채워지면 강화 또는 용병 계약 자동 실행
- 진영 강화는 성채 단계에 따라 상한 개방
- 대장 강화는 사망 후에도 유지
- 용병은 계약 종료 또는 대장 사망 후 철수

#### 완료 기준

- 골드가 개인 강화와 진영 기부 사이에서 의미 있는 선택이 됨
- 한 명이 진영 자산을 임의로 낭비할 수 없음
- 용병 수가 서버와 화면 성능을 과도하게 저하하지 않음
- 열세 진영이 회복할 수 있는 보정 장치가 작동함

### 7단계. 아트·UI·연출 통합

예상 기간: 전 단계와 병행, 집중 작업 8~12주

#### 목표

기능별로 섞여 있는 시각 표현을 하나의 상업용 베타 스타일로 통일한다.

#### 주요 작업

- 캐릭터 비율, 외곽선, 색, 그림자 기준을 담은 아트 바이블
- 인간과 오크 플레이어 기본 외형 확정
- 모든 몬스터의 기본, 공격, 피격 상태 통일
- 무기 종류별 1인칭 및 타 플레이어 스프라이트
- 구역별 벽, 바닥, 장식 소재 정리
- 이름표, HP바, 타겟, 알림 가독성 통일
- 로그인, HUD, 인벤토리, 대장장이, 진영 UI 통합
- 해상도와 확대 시 스프라이트 품질 기준 확정
- 사망, 무기 획득, 보스 등장, 성문 파괴 연출

#### 완료 기준

- 캐릭터, 배경, UI가 서로 다른 게임처럼 보이지 않음
- 가까운 거리에서도 주요 스프라이트가 깨지거나 잘리지 않음
- 화면 크기 변경 시 UI 겹침과 잘림 없음
- 투자 데모 영상에 사용할 수 있는 대표 장면 확보

### 8단계. 비공개 알파와 밸런스 검증

예상 기간: 6~10주

#### 목표

실제 사용자 행동을 기준으로 게임성과 안정성을 검증한다.

#### 테스트 단계

1. 내부 2인 테스트
2. 지인 5인 테스트
3. 10인 동시 테스트
4. 최대 목표 인원 20인 부하 테스트
5. 30~60분 장기 세션 테스트

#### 수집 지표

- 로그인 성공률
- 평균 세션 길이
- 첫 무기 교체까지 걸린 시간
- 첫 중간보스와 발록 도달 시간
- 사망 후 재도전 비율
- 구역별 체류 시간
- 무기 종류별 선택률
- 골드의 개인·진영 사용 비율
- PvP 처치 격차
- 클라이언트 오류와 서버 지연

#### 완료 기준

- 20인 접속에서 서버가 안정적으로 동작
- 30분 플레이 중 진행 불가 오류 없음
- 신규 플레이어가 핵심 순환을 이해함
- 특정 무기나 진영이 압도적으로 유리하지 않음
- 반복 플레이 의사를 보이는 테스트 사용자 확보

### 9단계. 투자·사업 제안용 베타 패키지

예상 기간: 4~8주

#### 목표

게임을 설명하는 것이 아니라 직접 보여주고 검증 자료를 제시할 수 있는 상태를 만든다.

#### 산출물

- 안정적인 공개 또는 초대형 베타 URL
- 3~5분 플레이 데모 시나리오
- 60~90초 소개 영상
- 게임 소개서와 핵심 시스템 문서
- 개발 로드맵과 인력·예산 계획
- 기술 구조도와 서버 확장 계획
- 사용자 테스트 결과와 개선 이력
- 경쟁 제품 및 시장 포지셔닝 자료
- 자산·코드 라이선스 목록
- 위험요소와 대응 계획

#### 투자 설명 핵심

- 브라우저 즉시 접속이 만드는 낮은 진입장벽
- PvE, 레이드, 진영 공성의 결합
- 무기 파밍과 진영 경제가 만드는 반복 플레이
- 커뮤니티와 IP 확장 가능성
- 실제 플레이 데이터와 사용자 반응

#### 지원사업·연구용역 설명 후보

- 경량 브라우저 기반 실시간 멀티플레이 기술
- 서버 권위 PvPvE 상태 동기화
- 접속 인원과 진영 격차에 따른 동적 밸런싱
- 설치 없는 게임 접근성과 사용자 진입 비용 감소
- 지속형 던전 상태와 복구 시스템

검증되지 않은 기술적 우수성이나 시장 성과를 과장하지 않고, 구현 결과와 측정값을 근거로 제시한다.

## 7. 기술 구조 개선 방향

현재 세 파일 중심의 구조는 초기 프로토타입에는 적합했지만 장기 개발에는 위험하다. 단계적으로 아래 경계를 분리한다.

### 클라이언트

```text
src/
  core/        게임 루프, 시간, 입력
  rendering/   레이캐스팅, 스프라이트, UI 렌더링
  world/       맵, 구역, 충돌
  combat/      공격, 무기, 피격 표현
  network/     Socket.IO 이벤트와 보간
  ui/          로그인, HUD, 인벤토리, 상점
  data/        무기, 몬스터, 밸런스 설정
```

빌드 도구 도입 여부는 0단계에서 결정하되, 브라우저에서 바로 실행 가능한 정적 배포 원칙은 유지한다.

### 서버

```text
server/
  app          서버 시작과 진단
  players      캐릭터, 진영, 접속
  rooms        공용 던전 상태
  combat       서버 권위 공격 판정
  monsters     AI, 사망, 리스폰
  items        드랍, 인벤토리, 골드
  factions     성문, 대장, 진영 금고, 용병
  storage      DB 저장과 마이그레이션
```

### 저장 원칙

- 서버가 캐릭터와 월드 상태의 최종 권한을 가진다.
- 브라우저 저장은 마지막 이름과 복구 힌트만 보관한다.
- DB 스키마 변경은 버전과 마이그레이션을 가진다.
- 캐릭터, 인벤토리, 공용 던전, 진영 상태를 분리한다.
- 저장 실패 시 서버 로그와 관리자 진단 화면에서 확인할 수 있어야 한다.

## 13. 첫 번째 공식 마일스톤

### Milestone A: Stable Foundation

목표는 화려한 신규 기능이 아니라 다음을 만족하는 안정 버전이다.

- 한글과 문서가 정상 표시됨
- 캐릭터와 성채 상태가 서버 재시작 후 유지됨
- 현재 전투와 멀티플레이가 회귀하지 않음
- 코드와 데이터의 주요 책임 영역이 정리됨
- 이후 무기 시스템을 안전하게 추가할 수 있음

이 마일스톤이 완료된 뒤에만 무기·인벤토리·골드 개발을 시작한다.
